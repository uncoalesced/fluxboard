## 1. Expanded row

### 1.1 Spotify / YouTube Music media controls

**Current state.** `QuickAccessRow.kt:63` holds six actions: `grid`,
`translate` (stub), `grammar` (stub), `clipboard`, `textedit`, `switchime`.
Nothing media-related exists. Declared permissions today are `INTERNET`,
`ACCESS_NETWORK_STATE`, `READ_MEDIA_IMAGES`,
`READ_MEDIA_VISUAL_USER_SELECTED`, `READ_EXTERNAL_STORAGE` (maxSdk 32) and
`VIBRATE`. No `<queries>` block.

**Proposed approach.** Split the ask in two, because the two halves have
wildly different costs.

*Transport control (play/pause, next, previous) - zero permission.*
`AudioManager.dispatchMediaKeyEvent(KeyEvent(KEYCODE_MEDIA_PLAY_PAUSE))`
routes to whichever app holds the active media session. No permission, no
`<queries>`, no app-specific SDK, works with Spotify, YouTube Music, Poweramp
and everything else identically. `AudioManager.isMusicActive()` (also
permission-free) gates whether the block is shown at all, so it does not
occupy the row when nothing is playing. Build the `KeyEvent` with real
timestamps the same way `sendRawEnter` does - the two-argument constructor
leaves `downTime` at zero and that has already bitten this project once.

*Track info (title, artist, artwork) - heavy permission, and I recommend
against it.* The only API that exposes now-playing metadata from an arbitrary
app is `MediaSessionManager.getActiveSessions(ComponentName)`, and it throws
`SecurityException` unless the caller holds
`BIND_NOTIFICATION_LISTENER_SERVICE` - which means shipping a
`NotificationListenerService`, sending the user into a special-access
settings screen, and thereafter having read access to the full text of every
notification on the device. For an app whose pitch is "zero telemetry, more
private than any existing option", that is the single most invasive
permission on Android and it will show up in the F-Droid anti-features
discussion.

The MediaBrowser route (connecting to a named app's `MediaBrowserService`) is
worse for a different reason: it needs `<queries>` entries naming Spotify and
YouTube Music by package, which is exactly the app-specific coupling you said
to avoid, and Spotify's service rejects transport control from non-authorised
clients anyway.

**Recommendation:** transport controls in v0.1.5, permission-free. Track info
declined by default. If you want it, it should be a separate, explicitly
opt-in feature with its own settings copy explaining the permission, and it
should ship no earlier than v0.1.7.

**Risk / fake-plausible flag: HIGH.** A media block that renders a
play/pause/skip cluster and a "Now playing" placeholder would look complete
in a screenshot and do nothing. Verification: the key-event builder is a pure
function with a unit test asserting keycode, both ACTION_DOWN and ACTION_UP,
and non-zero timestamps; the end-to-end behaviour needs a device with a media
app playing, and cannot be claimed done from code review.

**Open questions.**
- Confirm: transport-only now, metadata deferred? (my recommendation)
- If metadata is wanted eventually, is a Notification Listener acceptable at
  all, or is that a permanent no?

**Target:** v0.1.5 (transport). Metadata: unscheduled, needs your decision.

### 1.4 Direct-access button for the Emoji tab specifically

**Current state.** `handleKeyPress()` (`TypingKeyboardView.kt:665`) routes
literal string tokens: `"STICKERS"` opens `AppMode.EMOJI_PICKER`,
`"CLIPBOARD"` opens `AppMode.CLIPBOARD`. `EmojiPickerViewModel.selectTab(i)`
exists, where index 0 is Stickers and 1..n are the emoji groups. Nothing can
target a tab. The remap dialog writes any non-blank string into
`KeyDefinition.output`, and `LayoutValidator` only checks that four required
tokens exist *somewhere* - an unrecognised ALL-CAPS output is accepted and
silently does nothing.

**Proposed approach.** This is the shared prerequisite for both this item and
"remap presets" (5.8), so build it once: a small explicit action vocabulary,
parsed in one place, replacing the scattered magic strings.

```
sealed interface KeyAction {
    data class Text(val output: String)
    data class Mode(val mode: AppMode)
    data class Picker(val tab: PickerTab)      // Stickers | Emoji
    data object Shift / Delete / Enter / Symbols / Abc / SwitchIme ...
}
```

`"STICKERS"` stays a valid alias for the picker so custom layouts already
saved by testers keep working. `keyGlyph()` gains entries for the new tokens
(it is already the single label/icon table, per `KeyGlyphs.kt:43`).

**The one real cost:** targeting a picker tab needs the initial tab to reach
`EmojiPickerViewModel`, and that ViewModel is constructed by the hand-written
factory in `StickyKeysIME.kt:102` - Hilt does not build it - so a constructor
parameter means editing that factory. Cleaner: carry the requested tab
alongside `appModeState` in `MainIMEView` and call `selectTab` on arrival.
Either way, if this becomes a new method on `KeyboardController` it must be
implemented in **all four** implementors: `StickyKeysIME`, the wrapper in
`rememberInterceptingController`, `PreviewKeyboardController` in the app
module, and `NoOpController` in `KeyboardRecompositionTest`.

**Risk: MEDIUM.** Not conceptually hard, but it touches the key-press
dispatch path, which is also the recomposition-sensitive path. The hoisted
single `(String) -> Unit` handler must survive - see `KeyboardRows.kt:66` and
`KeyboardRecompositionTest`.

**Open question.** Should the new key open the picker at the first *emoji*
group (skipping Stickers), or at the last tab the user had open? Recommend
first emoji group - "last used" is a surprise when the key is labelled with
an emoji.

**Target:** v0.1.5, and it must land before 5.8.

## 4. Caps lock and shift behaviour

These two items share one design and one threshold constant, so they are
planned together as you asked.

### 4.1 Caps lock rework

**Current state, exactly.** `TypingKeyboardView.kt:676`:

```
LETTERS_LOWER     -> LETTERS_UPPER
LETTERS_UPPER     -> LETTERS_CAPS_LOCK
LETTERS_CAPS_LOCK -> LETTERS_LOWER
```

An unconditional three-step cycle with **no time window at all**. Around it:

- `TypingKeyboardView.kt:746` - any ordinary key press while in
  `LETTERS_UPPER` drops back to `LETTERS_LOWER`, so one-shot shift already
  works.
- `TypingKeyboardView.kt:194` - a `LaunchedEffect(shouldAutoCapitalize)`
  forces `UPPER` when auto-capitalize turns on and forces `LOWER` when it
  turns off. This can and does override a shift the user pressed deliberately.
- `TypingKeyboardView.kt:187` - a new input session resets the mode.
- Enter resets it explicitly at `:717`.

So what you are actually asking for is *close* to what exists. The behavioural
difference is at the second tap: today a slow second tap locks caps, and
turning shift back off from there costs a third tap. That is precisely the
"capslock state inconsistency" report - the user taps twice slowly meaning
"on, then off" and gets caps lock.

**Proposed approach.** A pure function, not inline `when`:

```
internal fun nextShiftState(current: ShiftState, sinceLastTapMs: Long): ShiftState
```

with transitions:

| From | Tap within window | Tap after window |
|---|---|---|
| Off | OneShot | OneShot |
| OneShot | Locked | Off |
| Locked | Off | Off |

Threshold: use `ViewConfiguration.getDoubleTapTimeout()` (the platform value,
300ms) rather than a hardcoded constant, so it matches every other double-tap
in the system and there is nothing to tune wrongly. It stays a single named
constant so it can be replaced with a preference later.

The auto-capitalize interaction must be fixed in the same change: an
autocap-driven `UPPER` has to be distinguishable from a user tap, or the
double-tap window measures from the wrong event and a user tap right after an
autocap transition reads as a double tap. Recommendation: autocap sets
`OneShot` but leaves `lastShiftTapAt` at zero, so the next tap can never be
read as a double.

**Risk / fake-plausible flag: HIGH - this is the item on the list most likely
to get a fix that looks right and is not.** A timing state machine written
inline in a composable is untestable, and "it seemed to work when I tried it"
is exactly how the third transition ends up wrong. Verification: the pure
function above with a table test covering all six cells, plus an explicit case
for "autocap fired, then the user tapped shift 50ms later" - the case that
distinguishes a real implementation from a plausible one.

**Open questions.**
- Confirm `Locked -> any tap -> Off` (my recommendation) rather than
  `Locked -> OneShot`.
- Should the threshold be user-tunable? Recommend no.

**Target:** v0.1.5.

### 4.2 Capslock state inconsistency (tracker overlap)

Your instinct is right - this resolves as a consequence of 4.1, and there are

### 4.3 Double-space inserts a period

**Current state.** Does not exist. `SPACE` (`TypingKeyboardView.kt:725`)
commits a space synchronously, then launches an async autocorrect that may
rewrite the text before the cursor, guarded by the `generation` token.

**Proposed approach.** A pure decision function, for the same reason as 4.1:

```
internal fun doubleSpaceReplacement(textBeforeCursor: String): String?
```

returning `". "` only when what precedes the caret is a space preceded by a
letter or digit; null after a period, after a newline, at the start of a
field, and after another space. The caller applies it with
`replaceTextBeforeCursor(1, ". ")` and sets `atSentenceStart`.

**The ordering trap, and it is real.** The space path already has an async
follow-up that rewrites text before the cursor. A double-space landing while
an autocorrect is in flight can eat the wrong span. This must be sequenced
through the same `generation` token that
`TypingViewModel.onSpacePressed()` returns - not a second, parallel guard.

**Risk / fake-plausible flag: MEDIUM-HIGH.** The naive version watches for two
taps in a window and inserts a period without ever looking at the text. It
demos perfectly and then produces `.. ` after a sentence, `. ` at the start of
a field, and a period after a newline. Verification: table test on
`doubleSpaceReplacement` with at least those four negative cases.

**Known limitation to state up front:** some hosts (and some OEM text fields)
already do this themselves, producing a doubled period. It is not detectable
from the IME. Recommend a settings toggle, default on, matching Gboard.

**Open question.** Default on or off?

**Target:** v0.1.5, immediately after 4.1 so they share the threshold.

## 5. Button removal, symbol pages, and layout fixes

**Read 5.9 before any of 5.1-5.6.** Five of these items are symbol-page work,

### 5.1 Duplicate voice button

**Current state.** Two mic surfaces, and the second one is decorative:

1. `TypingKeyboardView.kt:389` - a mic at the suggestion strip's right edge,
   which sets `comingSoon = "Voice input"`. This is the one you want to keep.
2. `KeyboardLayouts.kt:100` - the comma key carries `hint = "MIC"`. But

   key produces `. ? !`, never voice. The mic glyph on that key advertises

That is the actual defect, and it is worse than "duplicate" - it is a false
affordance.

**Proposed approach.** Drop `hint = "MIC"` from the comma key. It then behaves
exactly as it already does (comma on tap, `. ? !` on hold), and picks up the
corner dot marker that `TypingKeyboardView.kt:592` draws for keys with
alternates but no printable hint - so the hold becomes discoverable instead of
accidental. For your "general symbol access" ask, the same key's alternates
list is the natural place to put it.

**Open questions.**
- What should the comma key's alternates be? Current: `. ? !`. The strip fits
  about six comfortably. Give me the list rather than having me guess.
- Voice input itself remains a stub. Wiring it means either
  `RecognizerIntent` (hands off to another app, which on a de-Googled device
  may not exist) or `SpeechRecognizer` with `RECORD_AUDIO` (a real, prompted

**Risk: LOW.** **Target:** v0.1.5.

### 5.3 Long-press `$` for currency symbols

**Current state.** Not possible today, for a structural reason.
`longPressFor()` grants alternates from exactly two sources:
`PUNCTUATION_ALTERNATES` (which has entries for `.` and `,` only), or a
one-character `hint`. The symbol pages are built through
`KeyboardLayoutConfig.fromLegacyLayout()` (`:104`), which sets
`hint = null` unconditionally. **No key on either symbol page can have a
long-press alternate at all.**

**Proposed approach.** Falls out of 5.9: once the symbol pages are real
`KeyDefinition` rows, `$` gets `hint = "EUR-sign"` (or whichever you pick as
the primary) and its alternates come from the same field the hint does, per
the existing invariant.

**Sizing constraint.** The alternates strip uses 40dp cells
(`KeyboardRows.kt:242`). On a 360dp-wide phone nine cells exactly fill the
screen, and the strip clamps to stay on screen. Six is the comfortable
maximum.

**Proposed list, for you to confirm - I am deliberately not guessing a long
one:** `EUR £ ¥ ₹ ₩` (U+20AC, U+00A3, U+00A5, U+20B9, U+20A9), five entries,
`$` itself not included because the key already types it. Note that index 0 is
what a TalkBack long-press commits and where the finger starts, so the
most-wanted symbol must be first - tell me which that is for you.

**One optional refinement:** `₹` and `₩` are less universally present in older
system fonts than `£`/`¥`. `EmojiRepository` already filters by
`Paint.hasGlyph()` for exactly this reason; reusing that here would drop an
unsupported symbol from the strip rather than rendering tofu. Cheap, and it
reuses an existing pattern rather than inventing one.

**Open questions.** Confirm the list and the order.

**Risk: LOW** once 5.9 lands. **Target:** v0.1.5.

### 5.4 Add symbols to the number row - and the collision you should know about

**Current state.** `KeyboardLayouts.numberRow:43` is ten bare digit keys with
no hints, so no long-press behaviour at all.

**Three different asks in this brief all want the same slot on this row:**

1. 5.4 - "add symbols to the number row" (corner hints showing symbols)
2. 5.6 - shift-active shows each digit's shifted symbol
3. Section 8 - long-press a digit for its superscript and fractions

A key has one hint slot and one hold behaviour, and `KeyGestures.kt:128`
states the invariant plainly: the corner glyph and the hold output must come
from one field, because "the promise the superscript makes is precisely 'hold
this and you get that'". Satisfying all three naively breaks that invariant -
the hint would advertise `!` while the hold produced `¼`.

**Three coherent resolutions:**

- **A.** Hint = shifted symbol, hold = shifted symbol. Consistent, simple,
  and the fractions ask is dropped entirely.
- **B (recommended).** Hint = shifted symbol. Hold opens a strip whose
  **first** entry is that same shifted symbol, followed by the superscript
  and the fractions. The invariant holds - the hint is what a hold commits by
  default and what TalkBack commits - and all three asks are served.
- **C.** No hints on the digit row; hold gives fractions only; shifted
  symbols exist only while shift is armed. Loses all discoverability of the
  shifted symbols.

**This needs your explicit sign-off before any of 5.4 / 5.6 / section 8 can be
implemented.** It is the most tangled decision in the backlog and picking it
silently would be exactly the kind of quiet substitution the project rules
exist to prevent.

**Risk: MEDIUM.** **Target:** v0.1.5, gated on the decision.

digits pass through untouched.

row when `isUpper`. Small and localised. One nice consequence falls out for
free: `handleKeyPress`'s else-branch already drops `LETTERS_UPPER` back to
`LETTERS_LOWER` after any ordinary key, so typing a shifted symbol correctly
consumes a one-shot shift with no extra code.

**Risk: LOW.** Note that **no test currently covers row construction** -
`KeyboardRecompositionTest` measures skipping, not content. This change should
bring one.

**Open questions.** Confirm the shifted set is the standard
`! @ # $ % ^ & * ( )`. Depends on 5.4's decision.

**Target:** v0.1.5, with 5.4.

### 5.9 Extend remapping to symbols - the structural blocker

**Current state, and this is the important finding in this section.**
`LayoutEditorScreen` edits `layoutManager.activeLayout`, which is a
`KeyboardLayoutConfig` produced by `LayoutManager.buildDefaultLayout()` =
`KeyboardLayouts.letterRows(...)`. **It covers the letter pages only.**

The symbol pages are `KeyboardLayouts.symbolsPrimary` and `symbolsShifted` -
hardcoded `List<List<String>>` in the legacy form, converted at render time by

the label. They are not part of any layout config, are not persisted, and
cannot be edited, remapped, weighted, or given hints or alternates.

That single fact blocks 5.2, 5.3, and half of 5.4. It is the prerequisite for
this whole section, not a nice-to-have.

**Proposed approach, in two stages.**

*Stage 1 (v0.1.5) - data model only.* Promote the symbol pages into

already uses (`KeyboardTheme.kt:217`) so layouts saved by testers before this

`TypingKeyboardView.kt:126` stops calling `getLayoutForMode` + `fromLegacyLayout`
and reads the config instead. `LayoutValidator` grows page-aware rules. With
this in place, 5.2, 5.3 and 5.4 become ordinary content edits.

*Stage 2 (v0.1.6) - editor exposure.* A page switcher in
`LayoutEditorScreen` so the user can edit the symbol pages the same way they
edit letters.

persisted format. The old format must keep loading. Get this wrong and every

### 5.10 Text-selection toolbar visually inconsistent

**Current state, with the specific divergences.** `TextEditPanel`'s

### 6.3 Space-bar scrub bounds

**Bounds already exist** - see 0.3. But reading the scrub path turned up a
real defect that is not in the backlog:

`TypingKeyboardView.kt:165` - the `onScrub` handler calls
`typingViewModel.onWordFinished()` on **every scrub step**, and
`onWordFinished()` (`TypingViewModel.kt:241`) *learns* `currentWord` into the
personal dictionary before clearing it. So starting a scrub in the middle of a
word teaches the dictionary a word fragment. Those fragments then compete in
suggestions and, once seen twice, permanently veto autocorrect for themselves
(`PredictionEngine.kt:284`).

**Proposed approach.** Add `onWordAbandoned()` - clears without learning - and
call it from the scrub. Small, contained, and it removes a slow-acting
corruption of the personal dictionary.

Two smaller gaps also worth closing: there is no feedback when the caret hits
either end (the gesture reads as dead), and the 18dp activation plus the
acceleration ramp are constants with no user control. Recommend a haptic tick
at the boundary; leave the constants alone for now.

**Risk: LOW.** **Target:** v0.1.5. Note that the learn fix is a correctness
bug and should not wait.

### 6.4 Autocorrect - correcting the premise, then scoping the actual fix

**This item's framing in the brief does not match the code, and the difference
matters a great deal for scope.**

**What exists.** `PredictionEngine.getAutoCorrection()` is a genuine
autocorrect engine, not next-word prediction:

- weighted Damerau-Levenshtein trie walk over the mapped dictionary
  (`dfsEditDistance:451`), including the adjacent-transposition edit without
  which "teh" corrects to "ten";
- substitution costs weighted by real key geometry (`KeyProximity`), derived
  from the shipped row offsets, so "vall" resolves to "call" rather than the
  more frequent "all";
- frequency-penalised scoring with a credibility floor
  (`MIN_CORRECTION_SCORE`);
- run-on repair when a thumb hits `b`/`n`/`v`/`c`/`m` instead of the space
  (`splitOnMispressedSpace:357`);
- case restoration (`matchCase:423`) so corrections do not un-capitalise
  sentence starts;
- a two-strike personal-dictionary veto so deliberate words are left alone.

`PredictionEngineTest`, `AutoCorrectCoverageTest` and
`PredictionEngineConcurrencyTest` all exist.

**So there is no missing engine, and I am explicitly not proposing to write
one.** Nor am I proposing glide typing. What is broken is the plumbing
between the editor and that engine, in three specific, fixable places:

**(1) Autocorrect only ever fires on SPACE.** `handleKeyPress` calls
`getAutoCorrectionFor` in the `"SPACE"` branch and nowhere else. Ending a word
with `.`, `!`, `?` or Enter routes to `onWordFinished()` +
`onSymbolCommitted()` and never attempts a correction. A user who ends
sentences with punctuation sees autocorrect fire on maybe half their words.

**(2) `currentWord` is a write-only mirror that is never re-read from the
editor.** `TypingViewModel.currentWord` is built by appending on each letter
press and dropping one character on backspace. It is never resynced against
what is actually in the text field. So after any of: tapping into the middle
of a word, backspacing past a word start, selecting and retyping, using the
space-bar scrub, or pasting - it is wrong.

Every consumer then misbehaves, and one of them is worse than "gives up":
tapping a suggestion runs
`replaceTextBeforeCursor(getCurrentWord().length, "$suggestion ")`
(`TypingKeyboardView.kt:371`), so a stale length **deletes the wrong number of
characters from the user's text**. That is the "gives up on mid-word
backspace" report, and it is a data-loss-shaped bug rather than a missing
feature.

**(3) `onDelete()` decrements a local counter** rather than reading the text -
the same root cause as (2), and the reason backspace specifically is where
people notice it.

**Proposed approach - one root-cause fix, not three patches.** Derive the
current word from the editor rather than from a counter:

- add a bounded `KeyboardController.textBeforeCursor(n)` (48 characters is
  ample);
- resync `currentWord` from it on input start, on selection change, on
  backspace, and on any generation bump that was not a plain letter commit;
- route the IME's `onUpdateSelection` into `TypingViewModel` - it currently
  updates only `selStart`/`selEnd` on the service and tells the ViewModel
  nothing;
- then (1) becomes a small addition: run the same correction path on
  sentence-ending punctuation and on Enter.

**The invariant that must not break:** `CLAUDE.md` is explicit that a key
commit must never wait on a suspending lookup, and that `getCursorCapsMode()`
per keystroke is forbidden because it is a blocking IPC. The resync is one
bounded IPC on events that are *already* rare (session start, selection
change, backspace) - **never per keystroke**. If a design ends up needing a
per-keystroke read, that design is wrong.

**Risk: MEDIUM-HIGH.** It touches the hottest path in the keyboard.

**Fake-plausible flag: yes, and in a specific shape** - a "resync" that only
runs at input start would look done, pass a casual test, and change nothing
about the reported symptom. Verification: ViewModel-level tests against a fake
controller returning real text, asserting `currentWord` after backspacing into
a word, after a caret move, after a paste, and after a scrub.

**Scope boundary, stated so it is not crossed silently.** In scope: the
resync, the punctuation and Enter triggers, the wrong-length replace. **Not**
in scope, and each would be its own item if you want it:
- tuning `MIN_CORRECTION_SCORE`, `MAX_EDIT_COST` or the dictionary itself
  (data work, v0.1.6);
- bigram or context-aware correction (a real engine change);
- glide typing (a project, not a fix).

If correction quality is still poor after the plumbing fix, tuning is the next
lever and I will say so with measurements rather than guessing now.

**Target:** v0.1.5 for the plumbing. Tuning: v0.1.6.

### 6.5 `n` and `b` near the space bar read as space

**Current state.** No hit-test tolerance exists anywhere. Each key is a
Compose `Box` with a layout weight, and `keyGestures` commits its own
`keyOutput`; there is no key-rectangle table and no bias.

Note that this is already partly handled **after the fact**:
`splitOnMispressedSpace` exists precisely because a thumb hits `b`/`n`/`v`/
`c`/`m` instead of the space, and it repairs the resulting run-on at the word
level.

**Three options, honestly costed.**

- **A. Bias the space bar's touch area upward.** Cannot be done cleanly in
  Compose - a `pointerInput` cannot receive events outside its own bounds, so
  this needs the row restructured anyway. Rejected.
- **B. Grid-level hit testing.** One `pointerInput` over the whole key grid
  that maps a touch point to a key against a rectangle table with per-key
  bias. This is how LatinIME and FlorisBoard actually do it
  (`TextKeyboardLayout` in Floris is the reference). It is correct, and it
  **replaces the entire per-key gesture attachment** - `keyGestures`,
  the press-state plumbing, the alternates anchoring, the scrub, and the
  recomposition-skipping work all sit on top of the current arrangement.
- **C. Keep the post-hoc repair** and improve it (widen `spaceNeighbours`
  weighting, lower the split thresholds).

**Recommendation: C now, B as its own version.** B is the right long-term
answer and I am not going to pretend otherwise, but sneaking an input-layer
rewrite into a point release is exactly how the recomposition work gets
silently undone.

**Fake-plausible flag: HIGH, and I want to name the specific fakes** -
widening the space bar's layout `weight` (changes the visual layout, does not
change hit tolerance), or adding negative padding (does nothing to hit
testing). Both would look like the fix and neither is one.

**Target:** C in v0.1.5. B: its own version, not before v0.1.7, with a
proper design pass against Floris's hit testing.

## 7. Known bug - unrecoverable blank keyboard

**Current state.** Substantial defences already landed and I do not know
whether the bug still reproduces, because they went in without a confirmed
reproduction:

- `ThemeManager.resolveActive():78` - an unresolvable theme id now falls back
  instead of leaving `activeTheme` null forever, **and** repairs the stored
  preference so the next launch does not rediscover the same dangling pointer;
- unparseable theme files are renamed `.corrupt` rather than re-read and
  re-skipped every load;
- the available-themes list is never published empty;
- `KeyboardTheme.sanitized():64` drops any override combination that paints
  invisible keys - transparent glyphs, or glyph colour within 1.15:1 of the
  key fill, which two colour pickers defaulting to the same swatch reach in
  two taps;
- `ThemeFallbackTest` pins all of it.

**I am not going to invent a root cause.** Below are ranked hypotheses, each
with the observation that would confirm or kill it, followed by the thing I
actually recommend doing first - which does not depend on diagnosing anything.

### 7.1 Do this first: a recovery path that works regardless of cause

Add **Reset keyboard appearance** to `KeyboardSettingsScreen` (release build,
user-facing): resets `active_theme_id` and `active_layout_id` to the shipped
presets and deletes the custom theme and layout files.

This converts "unrecoverable short of uninstall and reinstall" - which is the
severity of this bug, not the blankness itself - into two taps, whatever the
cause turns out to be. It is small, it cannot regress anything, and it should
not wait for the investigation. **Highest value-per-line item in this entire
document.**

### 7.2 Hypotheses, ranked, each falsifiable

**H1 - theme override combination paints invisible keys.** Most likely
historically; largely mitigated by `sanitized()`. Discriminator: on a device
showing the fault, `run-as com.uncoalesced.stickykeys cat
shared_prefs/keyboard_preferences.xml` for `active_theme_id`, plus a listing
of `filesDir/themes`. If the active id names a custom theme with `keyStyle`
fill or text overrides, H1. **If this recurs on v0.1.2 or later, H1 is
falsified**, which is itself worth knowing. Note `run-as` works on the debug
build only.

**H2 - `LayoutManager` has the exact bug `ThemeManager` had.**
`LayoutManager.kt:46-60` is still `if (layout != null) _activeLayout.value =
layout`. A dangling `active_layout_id` silently keeps whatever was there
before, the preference is never repaired, and nothing sanitises a layout. It
is not blank *today* because the prior value is the built-in default - but it
is the same failure shape one edit away, and a custom layout that parses
while carrying junk outputs (which `LayoutValidator` permits, see 5.8) would
render keys with meaningless labels. **Recommend fixing the resolution to
mirror `ThemeManager` regardless of whether it is this bug** - it is roughly
ten lines and closes a whole class.

**H3 - Compose render failure in the IME window** (detached recomposer, or a
`ComposeView` outliving its ViewTree owners). Important discriminator: a
Compose hierarchy that draws nothing also has no semantics or gesture nodes,
so **H3 predicts dead keys, not functional invisible ones**. The report says
functional. That argues against H3 - but the report should be re-confirmed,
because "functional" may mean "the keyboard still had haptics", which is not
the same thing.

**H4 - background image drawn over the keys.** Eliminated by draw order: the
image and its overlay are drawn first, the key `Column` after
(`TypingKeyboardView.kt:246-284`). Listed so it is explicitly ruled out.

**H5 - extreme `KeyStyle` haze radius or border width** blowing out the
render node. Untested, cheap to bound-check.

### 7.3 Diagnostics to add now, so the next occurrence is conclusive

- A debug-build-only **keyboard state dump**, reachable from Settings,
  writing: active theme id, resolved theme JSON, whether `sanitized()` changed
  anything, active layout id with row and key counts, resolved panel height,
  the IME window frame, and the full `KeyStyle`. Build it into the existing
  `keyboard-core/src/debug` source-set pattern that `UsageRecorder` already
  uses - that shape is proven to be excluded from release by
  `verifyNoUsageLoggingInRelease`, so this adds **no** release surface. A
  `BuildConfig` flag would not do: `CLAUDE.md` records that R8 keeps a class
  referenced by a Hilt factory whatever a runtime boolean says.
- One debug-only log line in `resolveActive` recording
  `requested id -> resolved id, sanitized=true|false`.
- When capturing logs, capture from `cmd`, not PowerShell redirection -
  `CLAUDE.md` records a full round of wrong conclusions from a UTF-16 log file
  that `grep` silently matched nothing in.

**Risk:** the reset button and the `LayoutManager` fix are LOW. Root-causing
is unbounded until there is a reproduction.

**Open questions.**
- When it happened, were the keys genuinely still *typing*, or only
  vibrating? This single answer kills or promotes H3.
- Had the device ever had a custom theme or a custom layout saved?
- Is it reproducible on v0.1.2 at all, or only on v0.1.1 and earlier?

**Target:** reset button and `LayoutManager` fix v0.1.5. Diagnostics v0.1.5
(debug only). Root cause: open until reproduced.

## 8. Long-press number-key diacritics and fractions

**Current state.** `numberRow` has no hints and no alternates (5.4). The
mechanism needed already exists: a key with a one-character `hint` gets
`LongPress.Alternates(listOf(hint))` for free (`KeyGestures.kt:141`), and a
multi-entry strip needs only a table.

**Available precomposed Unicode.** Superscripts: `⁰` U+2070, `¹` U+00B9,
`²` U+00B2, `³` U+00B3, `⁴`-`⁹` U+2074-U+2079. Vulgar fractions: `¼` U+00BC,
`½` U+00BD, `¾` U+00BE, `⅐` U+2150, `⅑` U+2151, `⅒` U+2152, `⅓` U+2153,
`⅔` U+2154, `⅕`-`⅘` U+2155-U+2158, `⅙` U+2159, `⅚` U+215A, `⅛` U+215B,
`⅜` U+215C, `⅝` U+215D, `⅞` U+215E. (`↉` U+2189, zero thirds, exists;
recommend omitting it.)

**Reading your confirmed spec.** `1 -> ¹ ⅛ ¼ ⅓ ½` and `2 -> ² ⅔`. Both group
by numerator, superscript first, fractions ascending by value. Your `1` list
omits `⅐ ⅑ ⅒ ⅕ ⅙` (also numerator 1) and your `2` omits `⅖` - so the rule
appears to be "numerator group, familiar members only, capped around five".

**Proposed complete table - a proposal, not a fact.**

| Digit | Strip | Notes |
|---|---|---|
| 0 | `⁰` | superscript only; no common fraction has numerator 0 |
| 1 | `¹ ⅛ ¼ ⅓ ½` | exactly your spec; `⅐ ⅑ ⅒ ⅕ ⅙` dropped as obscure |
| 2 | `² ⅖ ⅔` | your spec was `² ⅔`; `⅖` added - **confirm or drop** |
| 3 | `³ ⅜ ⅗ ¾` | |
| 4 | `⁴ ⅘` | |
| 5 | `⁵ ⅝ ⅚` | |
| 6 | `⁶` | superscript only |
| 7 | `⁷ ⅞` | |
| 8 | `⁸` | superscript only |
| 9 | `⁹` | superscript only |

**Your two explicit questions, answered with recommendations.**

*Does `0` get superscript-only?* Yes. Recommend the same for 6, 8 and 9. And
note the pleasant consequence: **those four digits need no new code at all** -
a one-character `hint` already produces exactly "hold to get this", so
`hint = "⁶"` is the whole implementation for them. Only 1, 2, 3, 4, 5 and 7
need a multi-entry table.

*Consistent left-to-right ordering?* Yes - superscript first, then fractions
ascending by value, on every digit. Two reasons beyond tidiness: index 0 is
where the finger already sits when the strip appears, and index 0 is what a
TalkBack long-press commits (`TypingKeyboardView.kt:569`). A superscript is
the more likely intent than `⅞`, so it earns that slot.

**Cross-reference, and this is the constraint that decides the shape.** The
digit row's hint slot is contested by 5.4 and 5.6. Under recommendation **B**
there, the corner hint is the *shifted symbol* and the strip is
`[shifted symbol] [superscript] [fractions...]` - which pushes `1` to six
entries (`! ¹ ⅛ ¼ ⅓ ½`), exactly at the practical maximum for the 40dp cell
strip. That works, but it is tight, and it means the superscript loses index
0. **If you would rather the superscript keep the corner slot and the shifted
symbols live only in shift mode, that is option C in 5.4 - say so and I will
plan it that way.**

**Optional refinement.** `⅐ ⅑ ⅒` and some of the eighths are less reliably
present in older system fonts. `EmojiRepository` already filters with
`Paint.hasGlyph()`; reusing it here drops an unsupported character from the
strip instead of rendering tofu. Reuses an existing pattern rather than
inventing one.

**Emoji gate: safe.** I checked the regex in
`scripts/check-source-rules.sh:38`. It scans U+1F000-1FAFF, U+2600-2604,
U+2607-26FF, U+2700-27BF, U+2B00-2BFF and U+FE0F. Every character above lives
in Latin-1 Supplement (U+00B2, U+00B9, U+00BC-BE), Superscripts and Subscripts
(U+2070-209F) or Number Forms (U+2150-218F). **None of them will trip the
emoji rule.**

**Risk: LOW.** **Target:** v0.1.5, gated on the 5.4 decision.

## 10. Proposed implementation order

Four waves. Within a wave, order is flexible; across waves it is not.

**Wave 0 - safety and unblocking. No dependencies, ship first.**
A1, A2, A3, A4, A5, A6.

Rationale: A1 alone downgrades the most severe outstanding bug from
"reinstall" to "two taps", without needing a diagnosis. A2 closes the same
class of failure in the one place it has not been closed. A6 is a correctness
bug quietly corrupting the personal dictionary. None of these depend on any
decision from you.

**Wave 1 - input-layer correctness. One shared design review.**
A8 -> A9 -> A10 -> A11, then A7 and A20.

Rationale: A8 and A9 are the same UX pattern applied twice and must share one
threshold constant; doing them apart guarantees two constants that drift. A10
must precede A11 - triggering autocorrect on punctuation while `currentWord`
is still unreliable would spread the wrong-length replace to more code paths
rather than fewer.

**Wave 2 - layout data model, then everything downstream of it.**
A12 -> A13, A14. In parallel: A15 -> A16, A17, A18, A19.

Rationale: A12 and A15 are the two structural prerequisites, and six items sit
behind them. Attempting A16-A19 before A15 means editing the hardcoded legacy
string arrays, which is throwaway work that then has to be redone against the
new model.

**Wave 3 - presentation and additions.**
A21, A22, A23.

Rationale: none of these change behaviour that the earlier waves depend on,
and A21 is easiest once A12 has settled what a key can be.

**Held back from v0.1.5:** F1, F2, F3, F4, F5, F6, and anything gated on B1-B9
that is still unanswered when the wave reaches it.

**One scheduling judgement to flag.** Wave 2 is large - A15 is a persisted
format change with a compatibility requirement, and it gates four content
items that are themselves gated on B2 and B3. If B2 (the symbol-page
reference, requested four times historically) does not arrive, **A15 stage 1
can still ship in v0.1.5 while A16-A19 slip to v0.1.6.** That split keeps the
release moving without inventing a layout, which the standing instruction
forbids.
