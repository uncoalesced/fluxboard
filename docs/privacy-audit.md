# Privacy & Permissions Audit (Phase 31)

**Status:** Static portion complete. **Runtime traffic-capture portion NOT done**
(requires a physical device -- see "Outstanding" at the end).

> **History.** An earlier revision claimed no telemetry while ML Kit was still a
> dependency; that claim was false at the transitive level, because ML Kit pulls
> Google's CCT logging transport (`com.google.android.datatransport`). ML Kit and
> every Play Services dependency have since been **removed outright** rather than
> reconfigured. Section 2a records the verification.

This audit covers what can be verified by reading the source, dependency
declarations, and the merged manifest. It does **not** substitute for the
traffic-capture step, which must be run on real hardware during normal use.

## 1. Permissions

The final packaged manifest (verified from the merged/packaged manifest the
build produces) requests exactly:

| Permission | Source | Justification | Protection level |
|---|---|---|---|
| `INTERNET` | declared (app + transfer) | LAN device migration (Phase 27/28) and the ephemeral link-sharing relay (Phase 29/30). Nothing else makes network calls. | normal (install-time) |
| `ACCESS_NETWORK_STATE` | declared (app + transfer) | Detecting connectivity/local-network availability for the transfer feature. | normal |
| `VIBRATE` | declared (keyboard-core) | Keyboard haptic feedback (Phase 25), user-toggleable and off-capable. | normal |
| `CAMERA` | injected by `zxing-android-embedded` | Scanning the pairing QR code on the receiving device (Phase 27). Runtime-granted at point of use (the scan screen), not at first launch. | dangerous (runtime prompt) |
| `DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION` | auto-generated by AndroidX core | Self-scoped signature permission AndroidX adds for its own runtime `BroadcastReceiver`s on Android 13+. Not usable by other apps; no privacy surface. | signature |

Notes:
- **`REORDER_TASKS`** appears only in the **unit-test** merged manifest (pulled
  in by Robolectric); it is **not** in the shipped application manifest (verified:
  0 occurrences in the packaged release/debug manifest). No action needed.
- No location, contacts, microphone, phone, SMS, account, storage, or
  background-location permissions are requested. `CAMERA` is the only
  runtime-prompt permission.
- The permission set matches the expected set named in
  `.agent/rules/privacy-and-scope.md` (camera, network state, network) with the
  addition that camera here is for QR scanning rather than photo segmentation.

## 2a. Google CCT transport (`com.google.android.datatransport`) -- REMOVED, verified absent

ML Kit previously pulled `com.google.android.datatransport` (Google's CCT logging
transport) into the release build. Rather than reconfigure or suppress it, the
dependencies that carried it were removed:

- `com.google.android.gms:play-services-mlkit-subject-segmentation` -- deleted,
  along with the segmentation engine, its Hilt module and its call sites.
- `io.github.g00fy2.quickie` -- deleted. **Both** Quickie variants resolve to
  `play-services-mlkit-barcode-scanning`, so the "bundled" variant was not an
  escape; QR scanning is now `com.journeyapps:zxing-android-embedded` (Apache-2.0).

Verified after removal, by the same method used to find the problem:

**Resolved release runtime classpath** (`gradlew :app:dependencies
--configuration releaseRuntimeClasspath`), filtered for
`datatransport|mlkit|play-services|quickie|zxing` -- the only surviving matches
are ZXing:

```
+--- com.journeyapps:zxing-android-embedded:4.3.0
|    \--- com.google.zxing:core:3.4.1
```

**Release merged manifest** (`app/build/intermediates/merged_manifest/release/...`):

- occurrences of `datatransport`: **0**
- components under any `com.google.*` name: **none**

So `JobInfoSchedulerService`, `AlarmManagerSchedulerBroadcastReceiver`,
`TransportBackendDiscovery`, `MlKitInitProvider` and
`MlKitComponentDiscoveryService` are all gone from the shipped manifest.

**Release APK** (`app-release-unsigned.apk`, built with `isMinifyEnabled = true`),
scanning every `classes*.dex`:

```
classes.dex: datatransport=0 mlkit=0 gms=0
```

This is a statement about the built artifact, not about configuration intent:
there is no Google Play Services code, no ML Kit code, and no CCT transport code
in the APK.

## 3. Network code -- location and scope

Every network call in the entire codebase lives in the `transfer` module. No
network API (`okhttp`, `java.net.Socket/ServerSocket`, `HttpURLConnection`,
`Retrofit`, etc.) appears anywhere in `app`, `keyboard-core`, or `sticker-core`
main source. (`java.net.URLEncoder/URLDecoder` is used for nav-route encoding
only -- string manipulation, not I/O.)

Within `transfer`, the network code is:

| File | What it does | Reaches the internet? |
|---|---|---|
| `MigrationServer.kt` / `MigrationClient.kt` | `ServerSocket`/`Socket` for **LAN** device-to-device migration | LAN only |
| `LinkSharingManager.kt` | `ServerSocket`/`Socket` LAN-first path for link sharing | LAN only |
| `NetworkDiscoveryManager.kt` | Reads the device's own local IP (interface enumeration) | no I/O; local only |
| `RelayClient.kt` | OkHttp **WebSocket** to the relay for the off-LAN fallback | **yes -- the only internet-crossing code** |

So the only code that talks to a remote server is `RelayClient`, used solely for
the ephemeral link-sharing relay fallback -- exactly the one sanctioned network
feature. All migration and the LAN-first sharing path stay on the local network.
Everything else in the app (stickers, segmentation, GIF/WebP, the whole keyboard,
prediction, clipboard) is fully offline.

### Relay endpoint caveat (not a privacy leak, but a release blocker)

`RelayClient` currently points at `ws://10.0.2.2:8080` (an emulator-to-host
loopback stub) with a comment noting production would be `wss://relay.stickykeys.app`.
No relay is deployed. Off-LAN link sharing therefore does not function yet, and
when a real relay is deployed it must use `wss://` (TLS). Flagged for a hosting
decision; the relay by design brokers only opaque, client-encrypted bytes
(AES-GCM) and logs nothing.

## 4. Bundled assets -- nothing proprietary in the APK

The only binary blob bundled in any module's assets is
`keyboard-core/src/main/assets/base_dict.bin` -- the app's own prediction trie,
reproducible from `dictionary-tools/` (see `docs/dictionary-pipeline.md`). No
`.so`, `.tflite`, `.onnx`, `.aar`, or proprietary model file is bundled. With ML
Kit removed there is no longer any proprietary model in play at all -- bundled or
Play-Services-delivered -- so the `NonFreeDep` anti-feature previously required
for F-Droid no longer applies. See `docs/distribution/fdroid-notes.md`.

## Outstanding -- must be done on a physical device (NOT done here)

The traffic-capture confirmation cannot be done statically and is **not**
claimed complete:

- Install a debug build on a physical device.
- Capture traffic during ~10 minutes of normal use (create stickers, type with
  the keyboard, use prediction/clipboard, convert a video) using `adb`/`tcpdump`
  or PCAPdroid.
- **Expected result:** zero network traffic except during an explicit link-share,
  and even then only to the relay endpoint. Any other outbound connection is a
  finding.

Until that capture is run and its result recorded here, Phase 31 is
static-verified only.
