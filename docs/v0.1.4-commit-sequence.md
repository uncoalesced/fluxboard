# v0.1.4-ALPHA commit sequence

Everything on `development` since the last commit, in one working tree, from
roughly eight sessions with no intermediate commits.

## What was actually committed, and how it differs from the plan below

The tree was committed on 2026-08-06 as **eight commits at whole-file
granularity**, not the nine hunk-split commits set out below. The difference is
confined to one commit and is worth stating plainly rather than leaving to be
discovered from `git log`.

Everything that *could* be separated was: the palette, Auto Backup, the
clipboard double-write fix, the About link, the debug harness, the device
scripts and the docs each landed on their own. What did not separate is the
keyboard itself. Roughly seventeen files in `keyboard-core` reference each
other's new signatures -- `FieldKind`, the typing model, the alternates model,
the quick-access row and the IME service all changed together -- so no subset of
them compiles alone. Splitting them by hunk is possible interactively, where the
person doing it can see each hunk and rebuild after each commit; it is not
something to do blind, because a commit that does not compile violates
`code-conventions.md` and would not be discovered until someone bisected onto it.

So `feat(keyboard): privacy gates, symbol/alternates model, media transport` is
larger than any of the commits below, and its body lists the areas it carries.

**The rest of this file is kept as the record of the intended finer grouping.**
It is still the right shape if this is ever re-split -- for instance before an
upstream review that wants the privacy fix isolated -- and the hunk lists are
accurate against the tree as it stood.

## Why this needs `git add -p`, and where it can go wrong

Five files carry changes belonging to six different features:

| File | Features whose changes are interleaved in it |
|---|---|
| `TypingViewModel.kt` | privacy gate, private mode, double-space (B12), Enter learning, editor-derived learning, auto-capitalize gate |
| `TypingKeyboardView.kt` | privacy gate, currency/digit strips, quick-access + media row, Enter split, editor-derived learning, panel state reset |
| `StickyKeysIME.kt` | privacy gate, private mode wiring, Enter classifier, caret prediction on newline |
| `KeyGestures.kt` | F1 structural fix, currency key, digit hold-strip redesign, alternates drag slop |
| `MainIMEView.kt` | retiring `AppMode.STICKERS` (B13), panel height, mode reset on new field |

At whole-file granularity the first commit touching any of these drags in all of
it, and the requested grouping collapses into roughly one commit. So the
sequence below splits those five by hunk.

**The rule from `code-conventions.md` is that every commit compiles**, and hunk
splitting is exactly where that breaks. Verify each one rather than trusting the
grouping:

```bash
git stash push --keep-index --include-untracked && .\gradlew.bat assembleDebug ; git stash pop
```

Run that after staging and before each `git commit`. If a commit does not build,
the fix is almost always to pull one more hunk forward from a later commit.

**Considered and not used:** squashing commits 3-8 into one
`feat(keyboard): v0.1.4 keyboard work`. Coarser history, zero risk of a broken
intermediate. Joel chose the hunk-level split with the per-commit verify loop
instead; this is recorded only so the trade is on file.

Each commit below lists its hunks under **Take** and **Leave**. The `Leave`
lines matter as much as the `Take` ones -- a hunk pulled forward by accident is
how a later commit ends up referencing something that does not exist yet.

## 2. Auto Backup

Whole files.

```bash
git add app/src/main/res/xml/ \
        app/src/main/AndroidManifest.xml \
        docs/auto_backup.md
```

```
fix(privacy): scope Auto Backup so the dictionary cannot be uploaded

allowBackup="true" was declared with neither dataExtractionRules nor
fullBackupContent, which is the permissive default: everything in shared_prefs,
databases and filesDir eligible for upload. That included keyboard_database --
the learned personal dictionary and the clipboard history.

Both rule files ship, because the platform reads one or the other by version
and never both, and they are include-only. That shape is the mechanism: once a
scope contains any include, everything else is already excluded, so
keyboard_database appearing in neither list is what keeps it off Google's
servers. An exclude for a path that was never included is a no-op and lint
fails the build on it, precisely because writing one usually means the author
believed the opposite. Both files carry a comment saying so.

disableIfNoEncryptionCapabilities refuses cloud backup on a device with no lock
screen, where the payload reaches Google decrypted. There is no pre-Android-12
equivalent, so on those versions the omissions are the only defence.

Sticker bytes and the sticker index are omitted from cloud backup together and
travel on device-to-device transfer only. The 25MB cloud quota does not degrade
gracefully -- past it the OS silently stops backing the app up while continuing
to serve a stale snapshot -- and an index restored without its bytes presents
as a library of broken thumbnails.

Cannot be verified on a device: a real backup needs idle + power + Wi-Fi + 24h.
What was checked is that both files ship in the APK, the merged manifest
carries all three attributes, and every path named in them matches the code
that creates it -- a mistyped include backs up nothing and reports no error.

Item 4 of docs/auto_backup.md, the AES-256-GCM manual export tool, is not built.
```

```
fix(privacy): recognise password and PIN fields, and stop learning from them

Nothing in this codebase read the password input-type variations. inputType was
consulted in exactly one place, inside sendEnter, to choose between a newline
and the field's action. Incognito was driven solely by
IME_FLAG_NO_PERSONALIZED_LEARNING, which is a flag the host app has to set and
which Android's own TextView does not set for password fields.

So an alphanumeric password went down the ordinary letter path: each character
extended the tracked word, every keystroke ran a dictionary lookup whose
results were drawn in the suggestion strip above the keyboard, and the first
space or punctuation afterwards wrote the password into the personal dictionary
on disk. For a keyboard whose stated position is zero telemetry, a password
persisted to a local database the user cannot see is the same class of failure
as sending it somewhere.

fieldKindFor(inputType) now classifies the field. A sensitive one forces
incognito, and separately suppresses suggestion lookups and autocorrect. Those
two gates are deliberately distinct: incognito suspends writes only and leaves
reads working, which is right for a field the host merely asked not to learn
from and wrong for a password, where drawing dictionary matches for the prefix
is a shoulder-surfing hazard before any of it reaches storage.

TYPE_NUMBER_VARIATION_PASSWORD additionally gets a digits-only pad. It has no
ABC key on purpose: the field accepts nothing but digits, so an escape key
would only offer input the field refuses. The way out is the host's own focus
change.

Device-verified 2026-08-06 on a Redmi Note 11: all three text password
variations and the numeric one suppress the strip and learn nothing, and plain
number, phone and email fields are untouched. That negative half matters as
much -- a gate that also caught an amount field would silently kill suggestions
on ordinary typing.
```

```
feat(privacy): manual private mode for fields no signal can identify

The half of incognito that no EditorInfo signal can reach. A password field
announces itself through inputType and a host that sets
IME_FLAG_NO_PERSONALIZED_LEARNING announces itself through imeOptions, but an
ordinary message box holding a recovery phrase, a diagnosis or somebody else's
address looks exactly like every other message box. There is no signal to read
and therefore no honest automatic answer, so this is a labelled switch rather
than a heuristic on package names dressed up as detection.

Three parts of it are decisions rather than mechanics:

  - It resolves to FieldKind.PRIVATE rather than a second boolean threaded
    beside the first. isSensitive is true for it, so it travels the write gate
    (incognito) and the read gate (suggestions, autocorrect) without either gate
    growing a branch. effectiveFieldKind only ever upgrades NORMAL, so a PIN
    field keeps its digit grid.
  - It suppresses suggestions and autocorrect, not only learning. That is what
    makes it more than incognito with a button, and it costs the user the
    suggestion strip while it is on. The strip is itself a disclosure surface --
    it draws completions of the word being typed where anyone looking at the
    screen can read them -- so a switch that left it running would be armed and
    still leaking.
  - It is persistent and survives the end of an input session. The automatic
    signals are session-scoped and must be; a manual switch that cleared itself
    when the keyboard was dismissed would fail open, which is the direction that
    leaks. The padlock stays lit throughout and names which of the two is
    holding it.

Reachable from the keyboard's quick-access row and mirrored in Keyboard
settings; one stored flag behind both. Device-verified 2026-08-06.
```

```
feat(keyboard): move long-press alternates onto the key, not the character

A table keyed on a key's output cannot tell two keys apart that type the same
thing, and this had already produced one wrong behaviour and was about to
produce another. "1" is the output of a key on both the number row and row 1 of
symbols page 1, so the symbols page inherited the number row's fraction strips
and grew hold-affordance dots it was never designed to have. The new currency
key types the same "$" as digit 4's shifted symbol and would have collided the
same way; so would the PIN pad's digits.

Alternates now hang off KeyDefinition. PUNCTUATION_ALTERNATES is the one
surviving output-keyed case and is benign only because "." and "," want
identical behaviour everywhere.

Also here:

  - Symbol pages are part of KeyboardLayoutConfig rather than hardcoded string
    tables converted at render time, which is the single reason they could not
    be remapped, weighted, or given hints and alternates. They are optional with
    a fallback to the shipped pages, and toJson writes them only when they
    differ from the defaults -- always writing them would freeze today's pages
    into every custom layout and a user who reordered two letters would never
    receive a shipped symbol-page fix again.
  - A standalone currency key holding EUR YEN $ CENT RUPEE, opening on $ so a
    hold-and-release gives back the character printed on the key.
  - The digit hold strip no longer leads with the shifted symbol. That character
    is one shift-tap away where the whole row becomes real shifted-symbol keys,
    so the cell was a second route to something already reachable. A
    hold-and-release now commits the superscript.
  - Strips size their own cells, so length is bounded by the screen rather than
    by a test assertion. Drawing and selection read the same number; taking them
    from different places highlights a different cell than the finger is over.

Device-verified 2026-08-06: all ten digit strips render and commit, the
six-entry strip on "1" is reachable to its last cell, and symbols-page digits
have no strip at all.
```

Hunks: the `QuickAccessRow` call site including `onMedia` / `isMediaPlaying`,
and the `LocalContext` read.

```
feat(keyboard): media transport controls without asking for anything (B8)

Play/pause and skip for whatever the platform considers the active media
session, as their own row above the quick-access icons. No track title, artist
or artwork -- that half of B8 is still blocked and is what the B8 row now says.

The obvious API is MediaSessionManager.getActiveSessions(), which hands back a
MediaController per session and with it PlaybackState and full metadata. It is
gated behind BIND_NOTIFICATION_LISTENER_SERVICE, which grants the app the text
of every notification on the device. For three buttons on a keyboard that is a
disproportionate ask, and for this keyboard specifically it contradicts the
pitch. So this dispatches media key events through AudioManager -- the same
routing a hardware media button uses -- and needs no permission at all.

Two consequences are stated rather than hidden. There is no metadata, and that
is the scope rather than a stub. And isPlaying comes from
AudioManager.isMusicActive, which answers "is audio coming out right now"
rather than reading the session's state: a paused podcast reads false and a
browser video reads true. It picks a glyph and nothing depends on it. The
buttons are exact either way, because the key event reaches the active session
even when it is paused -- which is what makes resume work while the glyph says
play.

Two things that look like polish and are not. The row is drawn whenever the
toolbar is open rather than only when something is playing: gating it on
isMusicActive reads tidier and breaks the most ordinary case there is, because
pausing turns off the very signal the row was gated on and the control that
would resume it disappears. And both halves of each press are dispatched -- a
lone ACTION_DOWN is a held button to the receiver, and a hold on NEXT is
seek-forward in most players.

Seven icons is the ceiling for the action row, and it is arithmetic rather than
taste: at the 48dp accessibility minimum seven fill 336dp of a 360dp phone and
an eighth would have to overlap its neighbour. That is why the transport is a
second row rather than three more icons.

MediaTransportTest pins the key-code table. KEYCODE_MEDIA_NEXT is 87 and
KEYCODE_MEDIA_PREVIOUS is 88; transposed, both buttons work perfectly and point
the wrong way, which is invisible in a screenshot and obvious within a second
of holding the phone. Device-verified against a real player 2026-08-06.
```

```
fix(keyboard): eight defects found by the 2026-08-06 device pass

Every one of these was found on a phone, not in review, and each was invisible
to the unit tests that already covered the same code.

Learning trusted the keyboard's own buffer rather than the editor. Typing into
a TYPE_CLASS_PHONE field left it empty -- the editor's input filter drops
letters -- and put the letters in the personal dictionary anyway. That buffer
had already been taken away from destructive edits, where the suggestion strip
sizes its replacement by re-reading the field; learning was the other half of
the same gap and never got the same treatment. Every learn path now derives its
word from the editor via currentWordText(controller), and onWordFinished takes
the word as a parameter so the old mistake cannot be written again. One editor
read per word boundary, never per keystroke.

Enter learned the word it had declined to check. Enter deliberately does not
autocorrect -- correcting before it needs a blocking lookup, correcting after it
is too late in a field that has already sent -- but it still learned, so the one
path that skips the check was writing to disk unchecked. Measured: two sends of
"teh" put it in the dictionary at frequency 2, after which autocorrect stopped
fixing it permanently and the strip began offering it. In a send-on-enter chat
app that is the ordinary typing path, so the damage is routine rather than
exotic. Enter now splits on what it is: a submit abandons the word without
learning, a newline finishes it. Neither corrects. enterInsertsNewline is the
single classifier and sendEnter calls it, so what Enter does and what Enter
learns cannot drift apart.

sendRawEnter never predicted its caret, so onUpdateSelection treated every
newline as somebody else's edit, re-read the field and bumped the generation
token -- a blocking IPC on each Enter, in a codebase that avoids exactly that
everywhere else.

The alternates strip committed a different character than it highlighted.
Holding the currency key drew "$" selected and committed the euro sign. The
gesture loop tracked the finger on every pointer event, and a release is a
pointer event carrying a position that never left the key, so the strip's
default was overwritten before it could be committed. Invisible on all ten
digits, whose default is the cell under the finger anyway -- the right answer
from the wrong mechanism. The TalkBack path reads the default directly, so touch
and screen reader disagreed on the same key. Fixed with a 6dp movement slop.

Switching IME mode resized the window by 48dp. With the number row on -- the
default -- typing measured 956px and every other panel 830px, so opening the
emoji picker shrank the window and closing it grew it back, shoving the host
app's content up and down. The gate causing it carried a comment claiming it
prevented that.

Every copy was stored twice. OnPrimaryClipChangedListener is not once-per-copy;
redeliveries were measured 21ms and 253ms after the original. Suppressed inside
a one-second window. The window is load-bearing: suppressing on text alone also
swallowed a deliberate re-copy seconds later, which is worse than the duplicate
it fixed.

Auto-capitalize fired on password fields. initialCapsMode is non-zero for any
empty text field whatever its variation, so "correcthorse" was entered as
"Correcthorse" -- invisible in a masked field, which makes it worse rather than
more forgivable. Gated on the new FieldKind.isCredential, which is PIN and
PASSWORD only and deliberately not the broader isSensitive: that also covers
private mode, and a privacy switch must not stop capitalizing ordinary prose.

Focusing a new field left the previous panel open. Every other latch is
session-scoped; the app mode was the one that was not.

Also here, as permanent test infrastructure rather than scaffolding:

  - app/src/debug/ carries a field-type harness covering every inputType the
    keyboard classifies. It exists because the password gate had gone two
    releases unverified -- proving it needs a field the keyboard treats as a
    secret, and the only ones on a real phone are the lock credential and a
    Wi-Fi dialog. It lives in a source set rather than behind a flag for the
    same reason UsageRecorder does: a runtime boolean cannot make a class stop
    existing.
  - scripts/device/adb-safe.ps1 refuses to force-stop or pm clear whichever
    package is the bound IME. Both traps are documented in CLAUDE.md and both
```
