## Preflight

Several checks read app-private storage, which needs `run-as`, which works on
**the debug build only**. Release APKs are not debuggable and `run-as` answers
`unknown package`.

```bash
./gradlew.bat clean assembleDebug
```

```bash
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

Then, in one command each:

```bash
adb shell svc power stayon true
```

```bash
adb shell ime enable com.uncoalesced.stickykeys/.keyboardcore.ime.StickyKeysIME
```

```bash
adb shell ime set com.uncoalesced.stickykeys/.keyboardcore.ime.StickyKeysIME
```

Preflight traps, each of which has previously been mistaken for a real bug:

- **Keep the screen awake.** Taps sent to a sleeping device are silently
  discarded and every control reads as dead.
- **`ime list -a -s` is not `ime list -s`.** The first is the PackageManager
  scan, the second is what the input-method service will actually accept. If
  `ime set` answers `unrecognized IME ID`, uninstall and reinstall.
- **The id needs `.keyboardcore.`** -- the service lives in that module and the
  shorter `/.ime.StickyKeysIME` is rejected.
- **Never `am force-stop` the IME.** The system immediately switches to another
  keyboard and the next screenshot is of somebody else's. Tell them apart by the
  `?123` key and the teal enter button.
- **Do not capture logs by redirecting from PowerShell.** It writes UTF-16 and
  `grep` then matches nothing at all, including patterns that are certainly
  present.

**Baseline state.** Items 2 and 5 depend on an empty personal dictionary. Clear
it before starting:

```bash
adb shell run-as com.uncoalesced.stickykeys rm -f databases/keyboard_database databases/keyboard_database-shm databases/keyboard_database-wal
```

Then force the keyboard to rebuild it by switching to another IME and back
(**not** by force-stopping).

## 1. Suggestion strip deletes the correct span

The bug: the strip replaced `currentWord.length` characters, where `currentWord`
is a local mirror that only tracks what this keyboard typed. After any edit the
keyboard did not make, that length described text that was no longer there and
the replacement ate the wrong characters. The fix reads the span from the editor
at the moment of the tap.

The repro below deliberately uses two words of **different length** (8 and 3).
An equal-length pair cannot distinguish the fixed code from the broken code.

## 2. Space-bar scrub no longer poisons the personal dictionary

The bug: the scrub called `onWordFinished()` on every step of the drag, and that
function *learns* what it clears. Scrubbing out of a half-typed word wrote the
fragment under the caret into the dictionary. Once a word has been seen twice,
`PredictionEngine` treats it as deliberate and refuses to autocorrect it, so the
damage compounds and outlives the gesture.

Requires the cleared baseline from Preflight.

| 2.2 | Press and hold the space bar, then drag left at least 18dp until the caret starts moving, and release | Caret walks left through the text. No space is typed | | |
| 2.3 | Repeat 2.1 and 2.2 four more times, using `zqxjw` each time, so any learned fragment would pass the two-sighting threshold | | | |

## Findings from the partial pre-run

### F1 -- the symbols page digits inherited the fraction strip, unplanned

**Observed on device, not predicted.** On symbols page 1, the digit row `1`-`0`
now shows the small corner dot that marks a hold-available key, and holding a
digit there opens the same superscript-and-fraction strip the number row offers.

**Why.** `DIGIT_ALTERNATES` in `KeyGestures.kt` is keyed on the key's *output*,
and `"1"` is the output of a key on both the always-visible number row and row 1
of symbols page 1. Nothing distinguishes them, so both get the strip.

It is arguably an improvement -- the fractions become reachable without the
number row switched on -- and no test caught it because every test asserts the
number row's behaviour rather than the symbols page's absence of it. But it was
not designed, it changes the symbols page against the supplied reference (which
draws no dots there), and the first entry of the strip on that page is the
digit's *shifted* symbol, which is not advertised anywhere on that page because
symbols-page digits carry no corner hint.

**Re-investigated 2026-08-05 under the corrected page model, and RESOLVED.**

The three options recorded above were written on a wrong mental model. They
assumed "the numbers page" and "the symbols page" were separate places, so the
question looked like "which page should own the strip". They are the same place:
`KeyboardMode.SYMBOLS` has one digit row, and there is no separate numbers mode.
The real question was never which page wins, it was **why a lookup keyed on the
typed character could tell two keys apart at all.** It could not.

That reframing also showed the collision was about to get worse rather than
staying cosmetic. The currency key added this session types `$`, which is also
digit 4's shifted symbol; a numeric PIN pad types the same digits as the number
row. On the old output-keyed table, the currency key would have inherited digit
4's fractions and the PIN pad would have offered fraction strips on a passcode.

**Resolution applied:** alternates moved off the shared output-keyed table and
onto `KeyDefinition.alternates`, so a strip belongs to a key rather than to a
character. The number row carries the fraction strips, the symbols page digits
carry none, the currency key carries the currencies, and the PIN pad carries
nothing. None of them can reach each other's.

`NumberRowTest` asserts the PIN pad has no hold behaviour and
`SymbolPageLayoutTest` asserts the currency key and digit 4 hold different
strips, so the collision cannot silently return.

This is a structural fix rather than a product choice, which is why it was
applied rather than re-presented: every one of the original three options left
the same lookup shape in place and would have had to be re-litigated for the
currency key and again for the PIN pad.
